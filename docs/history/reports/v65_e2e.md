# C8 v65：双机同显存预算的端到端比较

正式计时已完成，两种模式各100条单轮请求、8组会话共17轮请求，无失败、无输出截断。
INT8 KV＋整理版 attention 的单轮/多轮 P95 和输出吞吐均改善。多轮 P50 增加7.16%，
单轮 P99 增加0.55%，这些结果仍保留。补充 profile 已完成，没有观察到匹配场景下
新 C8 decode 计算或 KV 写入变慢；它不能完整证明原计时中局部回退的全部因果。

## 实验口径

- 使用 `../run_deepseek/DeepSeek-V4-Pro-0813` 的 DEFAULT 双机参数，32个实际 rank，
  DP2×TP16、EP32、DSpark5、max_model_len135000、max_num_batched_tokens4096、
  max_num_seqs16、block32、FULL_DECODE_ONLY。客户端最多8个并发请求。
- 同为0.9总显存预算，使用各 dtype 自然形成的 KV 容量，不通过 block override 配平容量。
  两边可用 KV 显存均约18.98GiB/设备。BF16 的每 DP 容量324563 token；INT8 的两 DP
  分别567093/567076 token，容量增加约74.7%。图内存 BF16 约0.67–0.68GiB，INT8 约0.72GiB。
- 两节点分别核验实际 rank、DP/TP/EP 身份、预设参数及源文件/二进制 SHA。INT8 的
  T48 C4/C128 图确认使用 `clean=True` 新入口，T96/大 prefill 仍使用原有回退入口。
- 两模式使用同一冻结输入、输出长度、manifest、流式客户端。完成后逐请求核对请求
  SHA256 和 token usage。计时均未开启 profiler，补充诊断不计入下面的数字。
- 单轮来自用户 CSV 的长度联合分层采样100条，输入1166128/output195921 token；
  多轮保留8组的精确前缀 token ID，输出19767 token。多轮按固定 DP rank 分配，组内顺序执行。

正式结果目录：`results/e2e_c8_v65_bf16/`、`results/e2e_c8_v65_r1_int8/`。
比较器：`results/analyze_e2e_c8_v65.py`；机器可读汇总：`results/e2e_c8_v65_summary.json`。

百分比为 INT8/BF16−1；延迟越低越好，吞吐越高越好。

## 多轮局部回退

中位数位置由 BF16 的 group6/turn0 换成 INT8 的 group4/turn0；后一个请求本身
实际上从68.30s降低至42.74s。聚合 P50 的增加不是同一个请求慢7.16%。

但下面两轮确有明显配对回退，必须保留：

| 请求（零基索引） | 输入/output token | BF16总耗时/s | INT8总耗时/s | TTFT变化 |
|---|---:|---:|---:|---:|
| group4/turn1 | 51319 / 622 | 13.509 | 24.968 | 4.410s→4.924s |
| group6/turn0 | 42001 / 171 | 39.882 | 50.805 | 10.159s→25.648s |

第一轮回退主要发生在生成阶段，第二轮主要发生在首 token 前。组内顺序执行使
group4/turn1 在 INT8 中约于42.74s就能提交，BF16约于68.30s；其与其他长 prefill 的
重叠条件不同。这是需要 profile 检查的调度解释，不能仅凭请求时间直接定为 kernel 根因。
另有 group7/turn0 从3.860s变4.059s（+5.15%，约0.20s）。

8组各自的逐轮请求耗时之和均降低10.44%–17.25%。这不是覆盖上述单轮回退的替代指标，
也不是包含客户端轮间处理的精确会话 wall time。

## 补充 profile

`profile_multiturn_c8_v65.py` 复用原始8组17轮完整请求，仅加入每组固定的 `cache_salt`。
已核验本地 vLLM `CompletionRequest.cache_salt` 及 KV hash 实现：salt只参与缓存键，
不改变模型输入、prompt token ID、输出长度或组内前缀关系。两模式共用同一诊断 manifest；
这样无需修改 DEFAULT 预设或开启开发用 reset API，也不会复用正式测试遗留的整段缓存。
该诊断不替代、不覆盖正式计时。

按项目既有 serving profiler 约定和 `ops-profiling` 的多 rank 约束，使用 torch_npu/CANN
应用级 trace，选全局 rank0/16，各采两个最多8步窗口：初始混合 prefill，以及
group4/turn1 提交时。内核内优化依据仍为 `C8_V65_REPORT.md` 中的8份单算子 msopprof。
两类数据作用不同，不把通信任务交给单算子 msopprof，也不把带 profiler 的 wall time
用于吞吐/延迟验收。

INT8 诊断目录为 `results/e2e_c8_v65_r1_int8/`；BF16 诊断目录为
`results/profile_e2e_c8_v65_bf16/`。共8份 trace（2模式×2节点×2窗口），全部完成独立
离线解析并验证非空 kernel CSV。worker daemon 内自动解析的已知报错由离线接口处理，
不把该日志当成有效 CSV，也没有丢弃原始数据。Node1 原始 trace 保留在 Node1 相同绝对路径，
带 SHA 的分析 JSON 已复制到本机。汇总为 `results/e2e_c8_v65_profile_summary.json`，
生成器为 `summarize_e2e_c8_profile_v65.py`。

每个窗口均对齐实际8步 metadata；逐步使用导出的 host/device flow 关联，C4/C128
归类检查每个 target phase 恰有30/31个调用。无法解析的 flow 保持 unresolved。
根据 API 窗口与 trace 文件生成时间核对身份，不按 CSV 导出时间排序。

| 诊断场景 | BF16平均调用/us | INT8平均调用/us | 变化 |
|---|---:|---:|---:|
| Node0近4K长位置 prefill，C4 | 5426.64 | 5160.99 | −4.90% |
| Node1近4K长位置 prefill，C4 | 5409.30 | 5124.03 | −5.27% |
| Node0近4K长位置 prefill，C128 | 3005.14 | 990.34 | −67.05% |
| Node1近4K长位置 prefill，C128 | 3659.78 | 1211.87 | −66.89% |
| Node0近4K长位置 prefill，KV写入 | 34.44 | 16.34 | −52.55% |
| Node1近4K长位置 prefill，KV写入 | 47.33 | 16.74 | −64.63% |
| Node0 eager decode B3/Q18，C4 | 57.93 | 51.83 | −10.52% |
| Node0 eager decode B4/Q24，C4 | 65.22 | 50.73 | −22.23% |
| Node0 eager decode B3/Q18，C128 | 53.93 | 32.84 | −39.11% |
| Node0 eager decode B4/Q24，C128 | 58.54 | 34.55 | −40.97% |

近4K筛选要求当前预填充行已计算位置>=4096、总live query在3900–4100；Node0两模式
各9个合格阶段，Node1为BF16 14/INT8 12个阶段。不是完全相同的上下文和 co-batch。
eager decode 两种几何的 model execution padding 均为48，各模式各2个阶段，保留
实际 request rows；也不是固定地址同输入的 standalone 消融。没有合格 FULL graph
配对，因此不从这些窗口额外给出 graph 加速比。

第二窗口中，两模式的 Node0 都有4步纯 decode、4步混合 prefill，Node1均为8步
约4072个 prefill token 的混合负载。INT8 Node0 的244次新 C8调用直接在 trace 中出现。
与此同时，Node0 collective-communication activity union 为BF16约2796ms、INT8约2014ms；
Node1约1824/1895ms。这些是8步内包含数据传输和等待的活动区间，不等于纯等待耗时，
也不能与attention总时长相加还原请求延迟。

这组 profile 支持“实际服务里新 decode 和 KV 写入没有出现所采形状的计算回退”，
并确认混合 prefill、跨 DP 协同和 eager 路径确实存在。它没有复现并消融原计时请求的
全部调度时序，所以不能声称已经把多轮P50+7.16%或两轮配对回退完全归因到某一项。
约5.1ms的旧C4 prefill仍是大的计算成本，但本轮对照快于BF16；不能沿用历史“慢35%”
作为这次服务实验的结论。后续若继续优化，应单独优化长prefill回退入口和混合负载调度，
保留当前decode核心的广泛回归门槛。

已核对部署快照 `vllm_ascend/worker/model_runner_v1.py` 的
`_sync_metadata_across_dp`（824行附近）、重新 dispatch（3400行附近）及
`_post_process_cudagraph_mode`（6487行）：各 DP 取 graph mode 最小值；只要一个 DP
为NONE，所有 DP 都为NONE。因此某节点的纯 decode 步也可能随另一节点的 prefill
进入 eager。这与 INT8 第二窗口观测一致，不是 graph 缓存损坏的证据。没有修改这一协议。

两个 profile 服务的运行历史不同（INT8在正式测试后保留，BF16重新启动）；cache salt
隔离 KV 命中，但不能令所有硬件/代码缓存历史相同。后续的近4K筛选排除前两段未满
4096历史位置的 prefill，仍仅作为阶段诊断，不作为严格同地址单算子消融。

正式计时和诊断服务均已停止，两个节点的所有本轮 run-tag 进程均为空；
清理证据为 `results/c8_v65_service_cleanup.json`。29个受验收门槛保护的运行文件仍与
`results/c8_v65_acceptance.json` 完全一致，profile期间没有修改 kernel。

## 限制与启动记录

- 这是一次有界同配置对照，100条长度样本＋8组前缀会话，不是1000条、全会话集合或统计保证。
  单轮样本的极端 P99 长度尾部偏短，详见冻结 manifest 的分布审计。
- 原始 CSV 未包含可恢复的全部文本；保留输入/output长度与构造前缀，不等同于真实语义请求。
  8组中1组为按 token 关系推断的链，其余按实际 session_id 分组。
- BF16/INT8 数值差异改变生成轨迹：单轮100条完整生成序列没有逐位相同，多轮7/17相同。
  这不是模型质量评测；数值精度结论来自独立 kernel/真实历史激活检查。
- 闭环请求的开始时间随之前的完成时间变化，DP2/EP32 的跨组相互等待也可能不同。
  profile 只能把相同形状、相同阶段的任务当作 kernel 速度对照；不能相加重叠管线计数。
- 首次 INT8 启动 `results/e2e_c8_v65_int8/` 因自定义 INFO logger 被过滤，未通过路由证据门槛；
  没有计时请求。仅修正两个 logger 名并复核 adapter/graph 后使用 r1 重启，kernel 二进制未改变。
  失败记录及精确改动保留在 `results/c8_v65_logger_fix.json`，未删除失败尝试或择优替换计时。
